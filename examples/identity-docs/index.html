Identity, explained.
Built to be tested.

Kagi Identity の仕組み、アプリケーションとの接続、デプロイ、運用時の注意点を一つにまとめた技術ドキュメントです。機能の紹介だけでなく、実際に確認すべき境界と未検証事項も明示します。

重要 — 本番利用について
Kagi Identity は開発中のリファレンス実装です。CI の成功やデモの動作は、OIDC / OAuth / WebAuthn の正式な適合認証や、本番運用の安全性を保証しません。公開前に、脅威モデル・独立したセキュリティレビュー・対象仕様に沿った適合テストを実施してください。

このプロジェクトについて

Kagi Identity は Rust で実装された、パスキーを中心とする認証サービスと OpenID Connect / OAuth エンドポイントを提供するプロジェクトです。アプリケーションは Identity Provider（IdP）に認証を委譲し、認証結果を受け取ります。

クイックスタート

ローカル検証には Docker Compose を使用します。公開インターネット向けではなく、ローカル評価用の設定です。

git clone https://github.com/akiy2009/kagi.git
cd kagi
docker compose up --build -d
docker compose logs -f kagi
エンドポイント用途
http://localhost:8080/Identity ホーム
http://localhost:8080/signupパスキー登録
http://localhost:8080/demo組み込み RP デモ
http://localhost:8080/.well-known/openid-configurationOIDC Discovery
http://localhost:8080/jwks.json公開署名鍵

終了するときは docker compose down。ローカル DB と署名鍵も削除する場合のみ docker compose down --volumes を実行します。この操作は復元できません。

初回ログイン

  1. ローカルの /signup を開き、テスト用アカウントを作成します。
  2. ブラウザーと OS が WebAuthn / パスキーに対応していることを確認します。
  3. /demo からログインを開始し、認可リクエストからコールバックまでの挙動を確認します。
  4. ブラウザー開発者ツールとサーバーログを確認し、リダイレクト先・エラー・セッションの状態を照合します。

ローカル HTTP と localhost を前提とした開発設定を、公開環境へそのままコピーしないでください。

OIDC / OAuth の流れ

基本的な Web アプリ連携では、Authorization Code Flow と PKCE（S256）を使用します。クライアントは状態値を生成してリダイレクトし、認証後に登録済みのコールバックへ戻ります。

1. RP → IdPDiscovery を取得し、認可リクエストを生成
2. ユーザー認証IdP 側でパスキー等を使って認証
3. コールバックcode と state を検証し、サーバー側でトークン交換

Discovery と JWKS を確認する

curl -fsS https://YOUR-ISSUER/.well-known/openid-configuration
curl -fsS https://YOUR-ISSUER/jwks.json

issuer は構成した公開 Issuer と完全一致する必要があります。JWKS が取得できることだけでは、トークンの署名・audience・issuer・期限などの検証が正しいことを意味しません。

クライアント登録

RP の Client ID とコールバック URL は Identity 側に登録します。URL はプロトコル・ホスト・パスを含めて完全一致させ、ワイルドカードや任意の転送先を許可しないでください。

# 例示用です。実際の登録エンドポイント・認証方式は
# デプロイ中のコミットと docs/CLIENT_INTEGRATION.md を確認してください。
# 登録トークンはブラウザーへ公開しないこと。
  • 開発・プレビュー・本番でクライアントを分離する。
  • 登録トークンや管理トークンは Vercel のサーバー側環境変数など、秘密管理領域に置く。
  • クライアントシークレットを静的 HTML や JavaScript に埋め込まない。
  • 登録変更後、Discovery、認可、コールバック、ログアウトを再テストする。

Web アプリ連携

リポジトリには評価用のブラウザー SDK /static/kagi.js と、Vercel 上で動く静的 RP デモがあります。デモは接続確認のための出発点であり、本番アプリのセッション管理を代替するものではありません。

<script src="https://YOUR-ISSUER/static/kagi.js"></script>
<script>
  Kagi.configure({
    issuer: "https://YOUR-ISSUER",
    clientId: "YOUR_REGISTERED_CLIENT_ID",
    redirectUri: location.origin + "/auth/callback",
    scope: "openid profile email"
  });
  Kagi.login();
</script>

実際の SDK の API・エラー処理は利用中のコミットにある実装と照合してください。本番アプリでは、トークン交換・署名検証・セッション発行をサーバー側で行う構成を推奨します。

アーキテクチャと運用上の境界

Vercel はフロントエンドやサーバーレス関数に適していますが、Rust の HTTP サーバーをどの形で実行するか、ファイルシステム・接続・共有状態をどう維持するかを設計する必要があります。

コンポーネント考慮点
RP フロントエンド静的配信可能。Issuer と callback URL を環境別に管理。
Identity サーバー長時間稼働する Rust サービスの実行方式、HTTPS、ヘルスチェックが必要。
永続 DBローカル SQLite は開発向け。ホスト環境では永続ストレージか PostgreSQL 等を構成。
署名鍵・セッション鍵の永続化と保護、バックアップ暗号化、ローテーション手順が必要。
共有状態プロセス内のレート制限・リプレイ防止等は複数インスタンス間で共有されるとは限らない。
現在の検証状況
Vercel の RP デモはデプロイ済みです。一方、Identity 本体は過去の実行時ログで SQLite を開けずに終了した記録があり、Hobby プランではログ保持期間の制限もあります。最新の本番ヘルスチェックが成功するまで、IdP が正常稼働しているとは判断しません。

本番デプロイの基本

  1. 実行環境が Rust バイナリをサポートするか、コンテナや別の常時稼働ホストを使用するかを決める。
  2. 公開 Issuer、HTTPS、RP ID、WebAuthn Origin を一致させる。
  3. 永続データベース、バックアップ、接続上限、復元テストを設定する。
  4. 管理・登録トークンと署名鍵を秘密情報として管理する。
  5. ログ、メトリクス、アラート、ヘルスチェック、ロールバック手順を用意する。
  6. プレビュー環境でプロトコル・ブラウザー・障害復旧テストを終えてから段階的に公開する。

Vercel 環境変数

Issuer や DB 接続情報を設定する場合、Production / Preview / Development を分離します。秘密情報をクライアント側の NEXT_PUBLIC_ など公開環境変数へ入れないでください。実際に受け付ける変数名はリポジトリの docs/CONFIGURATION.md を参照してください。

データベースと永続性

SQLite はローカル開発に便利ですが、Vercel のエフェメラルな実行環境に保存したファイルが永続化されるとは限りません。プロセス再起動やインスタンス切り替えで DB や署名鍵が失われる構成は、認証基盤に適しません。

  • ホスト環境の永続 DB を使用し、デプロイをまたいだ読み書きをテストする。
  • DB バックアップには署名鍵等の機密情報が含まれる可能性があるため、暗号化とアクセス制限を行う。
  • 複数インスタンス構成では、DB だけでなくセッション、レート制限、リプレイ防止状態の共有方法も確認する。
  • バックアップからの復元と鍵ローテーションを実際に演習する。

セキュリティチェックリスト

以下は公開前の最低限の確認項目です。チェックを付けても自動監査や認証取得を意味するものではありません。

テストと検証

Rust 品質チェック

cargo check --locked --all-targets
cargo test --locked --all-targets
cargo clippy --locked --all-targets
cargo build --locked --release

実環境の確認順

  1. デプロイが READY であることを確認。
  2. ヘルスチェックとログでサーバーが起動し続けていることを確認。
  3. Discovery の JSON、issuer、JWKS の形式と到達性を確認。
  4. テスト用 RP クライアントで登録、認証、コールバック、UserInfo を検証。
  5. 無効な state / nonce、redirect URI 不一致、期限切れトークン、リプレイ等を検証。
  6. DB 再起動耐性、バックアップ復元、鍵ローテーションを検証。

CI の成功は、その CI で実行された範囲のみを証明します。実ブラウザー・実ホスト・本番データでの動作を自動的に保証しません。

対応範囲と制約

リポジトリの README では、WebAuthn、OIDC / OAuth 関連エンドポイント、トークン機能、PAR / DPoP 等の高度なプロファイル機能が説明されています。ただし、機能の存在と各 RFC の全要件を満たすことは別です。

  • 正式な OAuth / OIDC / FAPI / WebAuthn 適合認証を取得したと主張しない。
  • テスト対象のコミット、構成、データベース、実行環境を記録する。
  • 本番利用の判断には独立したレビューとプロファイルごとのテストを含める。
